# Design

## Context

См. [proposal.md](proposal.md). В репозитории уже есть `ios/Package.swift`, `ios/project.yml`, хранимый Xcode-проект, `.swift-format` и планы `Smoke`/`Full`. Локально подтверждены 11 Swift-тестов и четыре E2E-сценария. GitHub-репозиторий `AeShevch/kstati` приватный; файлов `.github/workflows`, `AGENTS.md` и конфигурации SwiftLint сейчас нет. Локальный Xcode — 27.2, XcodeGen — 2.46.0, `swift-format` — 6.4.4; SwiftLint и actionlint не установлены.

## Goals / Non-Goals

**Goals:** одна команда для локальных быстрых проверок; одинаковые проверки в CI; понятные правила для разработчика и агентов; диагностируемый и ограниченный по стоимости E2E; отсутствие изменений поведения приложения.

**Non-Goals:** запуск UI-тестов при каждом локальном коммите; автоматическое исправление кода в CI; обязательные Git hooks, самохостинг runner, релизный pipeline, CI для ещё не созданного backend, автоматическое включение защиты ветки.

## Decisions

### 1. Общие команды — источник истины для локального запуска и CI

Добавить небольшой исполняемый скрипт в `scripts/`, который вызывает `swift-format lint --strict`, SwiftLint, `swift test -j 1`, генерацию Xcode-проекта и проверку неизменности `project.pbxproj`; для UI выбрать аргументы `smoke`/`full` и записывать уникальный `.xcresult`. Скрипт определяет корень репозитория, проверяет наличие инструментов и версий, выбирает доступный iOS Simulator по модели/рантайму, а не по локальному UDID. Команды read-only, кроме XcodeGen: после генерации скрипт сравнивает хранимый проект с исходным и сообщает diff, не фиксируя его. Документация перечисляет локальный быстрый и полный наборы и версии инструментов.

Альтернатива — дублировать длинные команды в YAML и README. Это быстрее вначале, но позволяет CI и локальному запуску разойтись. Скрипт остаётся тонким: orchestration без собственной логики анализа Swift.

### 2. Два GitHub Actions workflow по цене и времени обратной связи

Workflow PR запускается на `pull_request` к любой ветке и `push` в `main`: проверка OpenSpec на Linux и проверки iOS на macOS (формат, SwiftLint, Swift-тесты, генерация проекта, сборка, `Smoke`). Это позволяет проверить текущую зависимую ветку PR к `codex/organize-ios-code-and-formatting` до её интеграции. Отдельный `Full` запускается при наличии явного PR label `run-full-e2e`, после интеграции в `main` и через `workflow_dispatch` после появления workflow в основной ветке; он выполняет четыре UI-сценария последовательно. Для обоих UI-прогонов сохраняется `.xcresult` при неуспехе с коротким сроком хранения. Повторные прогоны одного PR ограничиваются `concurrency`; permissions минимальны, команды не требуют секретов.

GitHub-hosted macOS расходует лимит Actions приватного репозитория и стоит дороже Linux ([GitHub billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)). Поэтому `Full` не дублирует `Smoke` на каждом PR. `macos-latest` меняет набор Xcode; workflow фиксирует доступный runner image и совместимый Xcode после проверки на GitHub, выводит версии в лог и сообщает о несовместимости явно. Источник версий — [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). Альтернатива — весь `Full` на каждом PR; она увеличивает цену и время без пользы для быстрого сигнала на текущем наборе из четырёх сценариев.

### 3. SwiftLint дополняет `swift-format`, а не заменяет его

Закрепить версию SwiftLint, добавить `.swiftlint.yml` с узким набором правил, проверяющих ошибки и сложность, и проверить фактические нарушения на текущих файлах до включения CI. Конфигурация не вводит второе правило отступов/переносов; формат остаётся за `.swift-format`. Если выбранное правило массово конфликтует с существующим кодом, отклонить его для этого change или исправить немногочисленные бесспорные нарушения отдельным коммитом; не сохранять длинный baseline или blanket suppression. Тесты проверяются применимыми правилами; допустимые `try!` в fixture не должны вести к исключению всего тестового дерева.

Правило «один основной тип на файл» и соседство тестов закрепляются в `AGENTS.md` и ревью: синтаксическое правило SwiftLint не различает основной тип и тесно связанный вспомогательный enum. Альтернатива — жёсткий собственный парсер; он усложнит поддержку и даст ложные срабатывания.

### 4. Правила агента короткие и проверяемые

Корневой `AGENTS.md` описывает расположение модулей и тестов, один основной тип на файл, исключение для маленьких деталей владельца, границы `MemoryCore`/`MemoryPersistence`/`MemoryOCR`, сохранение оригинала и подтверждённых значений, отсутствие секретов и пользовательского содержимого в логах, обработку ошибок, необходимость теста на изменённое поведение и команду проверки перед коммитом. Чеклист ревью фиксирует изменённый сценарий, проверку схемы/миграций, тесты и результат CI. Отдельный project skill пока не создаётся: он дублировал бы команды и правила; повторяющуюся процедуру можно вынести в skill после нескольких изменений.

ADR-001, ADR-002, ADR-003 и ADR-008 остаются действующими; предлагаемых отклонений нет. CI проверяет архитектурные инварианты, не вводя новый слой в приложение.

## Risks / Trade-offs

- Доступный на GitHub Xcode может отличаться от локального 27.2 → проверить runner image до фиксации workflow, вывести `xcodebuild -version`, закрепить совместимую версию и документировать расхождение.
- Приватный macOS CI тратит включённый лимит → короткий PR-набор, отмена устаревших прогонов, `Full` после интеграции или вручную, короткое хранение артефактов.
- UI Share Sheet зависит от среды runner → выполнить реальный GitHub `Smoke` и `Full`, сохранить `xcresult`, не считать локальный симулятор достаточным доказательством работоспособности CI.
- SwiftLint может дать много старых замечаний → измерить baseline до включения правила, выбирать узкий набор без blanket suppression.
- Локальный и CI-скрипт могут со временем разойтись → workflow вызывает те же команды скрипта, а документация указывает его как входную точку.

## Migration Plan

Сначала добавить правила и локальные команды, затем SwiftLint и workflow, после чего проверить их локально и в GitHub PR к ветке с предыдущим change. Для проверки `Full` поставить label `run-full-e2e`; после интеграции обеих веток в `main` проверить событие `push` и доступность ручного запуска. Сохранить неуспешный `.xcresult` как диагностический артефакт, исправить проблемы runner и только затем считать CI готовым. Откат — удалить workflow и конфигурацию линтера отдельным коммитом; продуктовые данные и код не мигрируют.
