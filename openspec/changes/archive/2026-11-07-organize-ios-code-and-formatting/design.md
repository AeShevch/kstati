# Design

## Context

См. [proposal.md](proposal.md). Сейчас SwiftPM-модули используют каталоги `ios/MemoryCore`, `ios/MemoryPersistence`, `ios/MemoryOCR` как source roots, а их тесты лежат в `ios/Tests/*Tests`. `ios/project.yml` задаёт пути targets XcodeGen; `ios/Kstati.xcodeproj` хранится в Git. Четыре UI-сценария находятся в одном `KstatiUITests.swift`; проверка ошибки записи требует ручного изменения прав на App Group, а другие сценарии зависят от состояния симулятора. `MemoryModels.swift`, `MemoryViews.swift`, `KstatiApp.swift` и `VisionOCR.swift` содержат несколько основных типов. `MemoryRepository.swift` содержит также `ShareCaptureID`. Конфигурации форматирования нет; `xcrun swift-format` доступен с текущим Xcode.

## Goals / Non-Goals

**Goals:**

- По структуре каталога сразу находить исходник, связанные тесты и fixtures каждого модуля.
- Дать каждому основному типу отдельный файл с соответствующим именем; оставить небольшие вложенные или тесно связанные вспомогательные типы рядом с владельцем.
- Получить воспроизводимое форматирование всех Swift-файлов с четырьмя пробелами и строгую read-only проверку формата.
- Получить поддерживаемый E2E-слой: сценарии читаются как действия пользователя, UI-локаторы централизованы, состояние тестов воспроизводимо, ошибки дают диагностические артефакты.
- Сохранить действующие API, target membership, ресурс PNG, миграции, тестовые сценарии и поведение приложения.

**Non-Goals:**

- Новые доменные абстракции, команды, протоколы, исправление capture ID, изменение ошибок или конкурентности.
- Разбиение `MemoryRepository` на новые сервисы только ради уменьшения числа строк; это один основной тип, а разделение его обязанностей требует отдельной проверки поведения.
- Сторонний E2E-движок, тестирование через приватные API iOS и отключение сети Mac как часть обычного тестового набора.
- CI, SwiftLint, Git hooks и правила агента: они планируются следующим change после стабилизации структуры и формата.

## Decisions

### 1. Исходники и тесты рядом, targets раздельно

Для `MemoryCore`, `MemoryPersistence`, `MemoryOCR` ввести `Sources/` и `Tests/` внутри каталога каждого модуля. SwiftPM source и test targets получают явные новые `path`. Для приложения использовать `KstatiApp/Sources/` и `KstatiApp/Tests/UITests/`; fixture host и PNG разместить в `KstatiApp/Tests/FixtureHost/` и `KstatiApp/Tests/Fixtures/`. Для расширения использовать `KstatiShareExtension/Sources/`. XcodeGen targets указывают на соответствующие подкаталоги, чтобы тесты не попадали в app target. Файлы entitlements и Info.plist остаются на текущих путях. Общий исторический отчёт `ios/Tests/README.md` перенести в `ios/TESTING.md` и обновить ссылки.

Внутри `KstatiApp/Tests/UITests/` разместить `Pages/`, `Support/` и `Scenarios/`; каждый Page Object и сценарный класс живёт в своём файле. Альтернатива — оставить общий `ios/Tests/` и зеркалировать имена каталогов. Она сохраняет меньше путей, но не решает запрос на физическое соседство тестов с кодом.

### 2. Один основной тип на файл

Разделить доменные модели из `MemoryModels.swift` по именам типов; `OcrStatus` может остаться рядом с `OcrSuggestion` как связанный enum. Разделить четыре View из `MemoryViews.swift`, `SharedMemory`, `MemoryStore`, `KstatiApp`, а также `TextRecognizer`, `VisionTextRecognizer`, `OCRProcessor` и `ShareCaptureID`. `MemoryRepository` остаётся одним типом в своём файле; локальные функции и небольшие детали реализации не требуют отдельных файлов. Публичные сигнатуры и уровни доступа сохраняются, если компилятор не требует минимальной правки для переноса.

Альтернатива — механически переносить каждую декларацию в отдельный файл. Это создаст лишнюю навигацию для тесно связанных вспомогательных типов.

### 3. Один форматтер, минимальная конфигурация

Добавить корневую `.swift-format` с четырьмя пробелами и согласованной длиной строки 120 символов; остальные настройки брать из `xcrun swift-format dump-configuration` для зафиксированной версии Xcode. Форматировать только собственные Swift-исходники и тесты, включая `Package.swift`, после переноса файлов. Проверять `xcrun swift-format lint --strict` на тех же путях. Не вводить второй форматтер.

Альтернатива — сразу добавить SwiftLint и набор opt-in правил. Для текущей задачи это смешивает механический формат с новыми правилами качества, которые ещё не согласованы.

### 4. E2E-слой поверх XCTest UI

Оставить существующий XCTest UI и реальный `ShareFixtureHost`: они уже проверяют системный Share Sheet, расширение и перезапуск. Page Objects (`MemoryListPage`, `AddMemoryPage`, `MemoryDetailPage`, `GroupsPage`) предоставляют действия и наблюдаемые элементы экрана; компонент для Share Sheet и fixture host инкапсулирует взаимодействие с другим приложением и системным UI. Сценарии сохраняют бизнес-утверждения в тестах, а локаторы по стабильным accessibility identifiers и ограниченные ожидания — в Page Objects. Координатный fallback для Share Sheet допускается только в одном компоненте с диагностикой и после попытки найти доступный элемент; произвольные `sleep` и проверки по порядку элементов не используются. Альтернатива — вынести общие действия в один базовый `XCTestCase`; это скроет навигацию и свяжет все сценарии наследованием.

Каждый сценарий запускается с чистым состоянием App Group через специальный аргумент запуска, обработка которого существует только в debug-сборке и выполняется до открытия БД. Тестовый переключатель ошибки записи также ограничен debug-сборкой и общим тестовым состоянием приложения и расширения; он заменяет ручной `chmod` и не влияет на release. Проверять, что переключатели не попадают в release-сборку. UI-тесты с общей App Group выполняются последовательно. Отдельные Xcode test plans `Smoke` и `Full` содержат соответственно короткий основной путь и все E2E-сценарии; файлы `.xctestplan` хранятся в репозитории и подключаются в `project.yml`. XcodeGen ссылается на готовые test plans, но не генерирует их содержание. [Apple рекомендует test plans](https://developer.apple.com/documentation/xcode/organizing-tests-to-improve-feedback) для разных наборов проверок; [XcodeGen поддерживает ссылки на них](https://github.com/yonaskolb/XcodeGen/blob/master/Docs/ProjectSpec.md).

При провале сохранять `xcresult` и снимки экрана; сообщения Page Objects указывают ожидаемый экран и элемент. Прогон `Full` дважды подряд на одном симуляторе без `simctl erase` проверяет изоляцию тестов. Отдельный офлайн-прогон остаётся специализированной проверкой и не блокирует обычный E2E-набор.

### 5. Проверять эквивалентность до и после переноса

Сначала записать baseline команд и результатов, затем переносить файлы без правки логики, обновить SwiftPM/XcodeGen и инструкции тестирования, сгенерировать Xcode-проект, а форматирование провести отдельным шагом. После этого перевести существующие UI-сценарии на Page Objects и test plans без потери проверок. Сравнить доступные test targets и сценарии, выполнить Swift-тесты, сборку всех targets и E2E-наборы. Проверить, что повторный `xcodegen generate` не меняет `project.pbxproj` при той же версии XcodeGen.

ADR-001 (Swift/SwiftUI), ADR-003 (границы домена) и ADR-008 (паттерны по необходимости) остаются действующими. Отклонений от принятых ADR нет.

## Risks / Trade-offs

- Перенос тестов может исключить их или PNG из target membership → проверить `swift test`, `xcodebuild -list`, fixture host и сквозной Share UI-тест.
- Сброс App Group может затронуть данные вне теста → включать его только в debug-сборке по явному аргументу и запускать UI-тесты на отдельном симуляторе.
- Системный Share Sheet меняет дерево доступности между версиями iOS → держать поиск и fallback в одном компоненте, сохранять диагностику при ошибке.
- Параллельные тесты конфликтуют из-за общего App Group → выполнять UI-набор последовательно и дважды без очистки симулятора проверять независимость сценариев.
- Массовое форматирование усложнит просмотр diff → отделить перенос и форматирование по коммитам; перед форматированием не менять поведение.
- Перенос деклараций может вскрыть зависимости от `private` или порядка файлов → изменять только необходимую видимость, проверять публичный API и сборку всех targets.
- Результат `swift-format` зависит от версии инструмента → зафиксировать версию Xcode/`swift-format` в инструкции и использовать один и тот же инструмент для форматирования и проверки.

## Migration Plan

Изменение применяется к исходникам в одном репозитории: перенести файлы, обновить пути targets, пересоздать Xcode-проект, форматировать, перевести тесты на E2E-слой и прогнать проверки. Отдельной миграции пользовательских данных нет. При регрессии откатить соответствующий коммит переноса, форматирования или E2E-слоя; схема SQLite и оригиналы пользовательской сборки при этом не меняются.
